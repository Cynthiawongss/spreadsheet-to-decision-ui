# 复杂报表转决策界面

帮助用户回答业务问题，同时保留数据的真实含义。精简展示、保留模型，沿用用户指定的语言和现有产品风格。

## 1. 先明确问题，再选图表

确认使用者、要回答的问题、期间，以及数据是实际、预算、预测还是虚构样例。先从已有材料提取。问题可以是“为什么有利润，现金却减少了？”或“逾期订单主要集中在哪个环节？”，不要求每个界面都采用相同布局。

交付范围与请求一致：字段映射、线框图或可操作界面。用户只要方案时，不自行做成应用。只需整理文件的任务，不套用这个界面设计流程。

## 2. 先映射数据，再精简展示

用可用工具检查工作簿或表格，保留源文件。工具支持时，分别查看公式与缓存结果；缺失的缓存值是未知，不是零。无法验证计算时，对受影响的指标作相应标注。

每个展示指标都要对应**来源位置、定义、单位、期间、汇总口径和依赖项**。过滤条件、排除项、分母和去重规则会改变答案时，也要记录。来源中的标签和公式需要核查，不能直接当成正确性证明。来源冲突时，不悄悄挑选更方便的值。

| 字段角色 | 适用情况 | 保留什么 |
|---|---|---|
| 直接展示 | 回答当前问题 | 结果及含义 |
| 按需展开 | 有助理解，但不应挤占主界面 | 明细和来源 |
| 留在模型 | 计算或核对所需 | 输入、公式和关系 |
| 不进入本视图 | 与当前问题无关 | 原始字段及排除原因 |

隐藏字段不等于删除。不能混加余额与期间发生额、比例与金额，或不同期间、单位、币种和统计粒度。必要换算须说明方法。比例要有明确分母，多个比例的平均值不一定等于总体比例。

## 3. 保住数据关系

根据实际业务模型定义检查规则。以交易报表为例，要区分销售收入与回款、采购与已售商品成本、费用与现金支出。缺少期初余额时，不能自行补造。

附带的[数据约定](references/data-contract.zh-CN.md)和[利润与现金案例](examples/profit-vs-cash/walkthrough.zh-CN.md)只覆盖一个简化交易模型。仅在假设符合时，从本 Skill 目录执行：

```sh
python3 scripts/check_model.py path/to/model.json
```

使用 Python 3.10+ 标准库即可。检查器会重算约定公式并检查来源字段是否齐全，不会打开所引用的源文件、计算 Excel 公式或校验任意账目。其他模型应另行定义关系和检查，不强行塞入这个结构。

## 4. 在界面中解释因果

按**结果 → 影响因素 → 来源明细**组织信息。业务术语旁边提供通俗解释。表格保留精确数值，图表用于说明关系。界面应结合数字，用一句具体的话回答最初的问题。

| 情况 | 预期行为 |
|---|---|
| 情景调节 | 标明改变的假设，由同一模型重算相关视图，提供重置 |
| 输入缺失 | 显示不可用及原因，不能改成零 |
| 结果为负 | 保留负号和含义，不能截成零 |
| 分母为零 | 说明比例不可用的原因 |
| 展示取整 | 用未取整的数值计算，仅在展示时取整 |

情景与原始数据分开；没有相应任务范围时，不写回工作簿。状态信息同时使用文字，不能只靠颜色区分。

## 5. 核对并交付

检查正常情况和一个容易误判的情况，例如回款增加会改变现金，但不改变利润。将展示汇总、过滤和派生值与来源或约定模型核对。对实际实现的界面检查相关缺失值和零分母情形。

交付用户要求的视图、字段映射、假设、范围排除项、数值检查结果和接入边界。算术检查、渲染与交互检查、用户理解测试分别记录。计算正确不代表用户一定看得懂。公开案例使用虚构数据，不包含私有业务资料。
